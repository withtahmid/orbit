# Transactions (web)

> A filterable, paginated transaction ledger with a totals summary, detail sheet, and new/edit drawers; dispatches to cross-space data in the personal sentinel space.

## Route(s)

- Path: `ROUTES.spaceTransactions(id)` -> `/s/:spaceId/transactions` (`apps/web/src/router/routes.ts:15`).
- Lazy-imported in `apps/web/src/router/index.tsx:28`, mounted at `apps/web/src/router/index.tsx:160-162` under `SpaceLayout`.
- Guards: `ProtectedRoute` -> `CurrentSpaceProvider` -> `SpaceLayout`. Personal-aware: when `space.isPersonal` it switches every query and replaces the account filter source with `personal.ownedAccounts`.

### Pin integration (inside NewTransactionSheet)

- `FieldPin` adapter (`NewTransactionSheet.tsx:843`) takes the current form value + the loaded pin value and decides which `PinControl` state to render:
    - pin exists, value matches → `pinned` (click unpins)
    - value present, doesn't match pin → `pinnable` (click pins, replacing the old)
    - pin exists, value is empty → **hidden** (the user has explicitly opted out of the pin for this entry; the button would otherwise read "Pinned" while the form shows "No event" and clicking would silently destroy a team-wide default).
    - no value, no pin → hidden.
- `available={!pinState.isPersonal}` hides every FieldPin on `/s/me` since pins don't apply there in v1.
- `canPin={canEdit}` on envelope/event fields renders the button disabled for viewers; account fields use `canPin={true}` since any member can manage their own per-user pin.
- Hydration `useEffect` per form is the cold-cache fallback only — the field initializers seed account/envelope/event synchronously from `pinState.pins` when the pins query is warm, avoiding a Radix Select remount bug that wiped the event pin on "Save & add another" (`NewTransactionSheet.tsx:1546-1558`).
- Expense form's envelope chip meta shows `pinned` vs `selected` (`envelopePinnedAndActive`, `NewTransactionSheet.tsx:1543,1733`). There is no "category default" state anymore — migration 050 dropped the category→envelope default entirely, so the envelope is always an explicit pick (pin, previous pick, or manual choice), and while empty the row renders as a labeled required picker rather than a collapsed chip.

### Kept date (inside NewTransactionSheet)

Separate mechanism from the server-side Account/Envelope/Event pins above, and deliberately a separate **vocabulary**: `PinControl variant="keep"` renders a `CalendarClock` glyph with "Keep" / "Keeping" instead of the Pin glyph with "Pin" / "Pinned". Those pins are _defaults_ ("which account do I usually pay from?"), stored in Postgres, two of them team-wide, meant to outlive the session. A kept date is a _mode_ ("which day am I entering for right now?") that is wrong to carry forward. One word spanning both would teach the user that "Pinned" means anything from _forever, shared with my partner_ to _until I stop for the evening, on this device_. Same button geometry, states and focus ring — consistency of form without conflating the concepts.

Solves: logging a day's transactions after midnight, or two days late, meant re-picking the same past date on every form.

- **`localStorage`, not Postgres and not `sessionStorage`.** Session scope sounds like the right lever for "don't let it live too long", but the idle window below already enforces that, and session scope silently drops the kept day on a refresh / PWA cold start / iOS tab eviction — mid-sitting, looking identical to "nothing is kept", which is exactly when a wrong date gets saved unnoticed.
- **Sliding 3h idle window**, refreshed by `touchDatePin()` in every form's mutation `onSuccess`, and cleared on sign-out (`AuthStore.clearAuth`, which `App.tsx`'s 401 handler also calls — on a shared machine the next user's first entry must not inherit the previous one's backfill day). A fixed TTL from the moment of keeping got the canonical case wrong: keep "yesterday" at 00:30, sleep, and a 12h timer is still live at 10:00 next morning, silently back-dating the day's first coffee. 3h rather than 6h because that same case is only 5.5h idle — a sitting is minutes to an hour, over-expiring costs two taps, under-expiring puts a wrong date in the ledger.
- **`KeptDateBanner`** renders a warn-toned full-width strip at the top of each form body whenever `keptDay !== todayDayKey()`. This is the one state in the sheet that can silently write a transaction to a date the user never looked at, and the date is not just a display field — it's the period key for envelope spend, allocations and Budgets. A chip in a hint slot is not proportional; someone in backfill rhythm reads Amount → Envelope → Save. It takes the open row's `currentDay` because the two diverge the moment the user hand-picks another date for one entry: the chip flips to "Keep" (off), which reads identically to "nothing is kept", while the _next_ form still opens on the kept day. Two strings — `Dating new entries to Aug 18` when they match, `This entry: Aug 20 · new entries return to Aug 18` when they don't. The announcement rides a separate, permanently-rendered `.of-sr-only` span, **not** a `role="status"` on the banner. An always-mounted wrapper was tried first, but it needed `:empty { display: none }` to avoid costing 16px of `.nt-form` gap on every form — and a live region inside a `display:none` subtree isn't monitored at all, so un-hiding and filling it in the same frame reproduced the exact failure the wrapper was added to prevent. The sr-only span is `position: absolute`, so it's out of flow, costs no gap, and is always observed — the same pattern the three money fields use. The banner is informational + a Stop action and deliberately does **not** rewrite the open form's date (surprising a half-filled row would be worse than the thing it guards) — so `DateField` separately paints a warn edge on the picker trigger whenever the row is back-dated at all, because pressing Stop unmounts the banner _and_ flips the chip, and without it the corrective action would strip every remaining signal.
- **Monotonically advancing time, never the raw clock.** `defaultEntryDateTime()` returns `keptDay + (time of day when kept) + (real seconds elapsed since)`, clamped at `23:59:59`. Identical to the live clock until midnight — and that's the point: with a frozen day and a live clock, an entry typed at 00:10 lands ~23h _before_ one typed at 23:50 on the same kept day, walking the batch backwards through the ledger. Clamping instead of wrapping keeps a batch ordered right up to the clamp; past it every entry shares `23:59:59` and the uuid tie-break returns, which is accepted (a long evening sitting only) rather than fixed with a counter. **Seconds are carried** (the string is `YYYY-MM-DDTHH:mm:ss`) because `transaction_datetime` ties break on a random uuid, so a rapid batch with identical stamps renders in arbitrary order. That makes seconds load-bearing, and every path that round-trips a datetime must preserve them: `EditTransactionSheet` hydrates via `toInputDateTimeSeconds` (`lib/dates.ts`) and `TransactionDatePicker.commitDraft` both serialises with seconds and threads `draftSeconds` through every `makeAppTzDate` rebuild. That includes the picker's `Now` preset, which drops **only milliseconds**: zeroing its seconds made "Now" the earliest second of its minute, so a row committed at 10:00:20 stored 10:00:00 and sorted ahead of rows entered at :05 and :12 — the same inversion, through the one path that skipped the threading. The Now chip is unaffected either way, because `setNow` hands the _same Date object_ to both `setDraft` and `setNowBaseline`, so the `getTime()` equality that lights it holds regardless of seconds.
- **`readDatePin` must stay emit-free** — it's the `useSyncExternalStore` snapshot, so it runs during render. Discarding a stale record calls the private `purge()`; only `writeDatePin`/`clearDatePin` `emit()`. `touchDatePin()` also doesn't emit: the snapshot value is unchanged, so there's nothing to re-render.
- **`isRealDay` round-trips through `fromInputDate`/`toInputDate`**, not just the `\d{4}-\d{2}-\d{2}` regex: `Date.UTC` silently overflows `2026-13-45` to 2027-02-14, so a corrupt stored value would move every subsequent entry to a date nobody chose.
- Global rather than per-space, on purpose: a sitting can span spaces.
- Not wired into `EditTransactionSheet`: editing an existing row must keep that row's own date. Arithmetic is a property of _typing an amount_; a kept date is a property of _creating_ a row.

### Inline calculator in money fields

Every money field in the transaction sheets accepts arithmetic — `1200+340+85`, `3*250`, `(400+50)/2`. A capability that applies to some money fields and not others is worse than one that applies to none, because the user can't form a rule. Covered: the hero amount (income / expense / transfer, plus the edit sheet) via `OrbitAmountCard`; the transfer **fee** via `OrbitCalcInput`; the adjustment **actual balance** via `useCalcField` wired directly into its bespoke drift-card input (`allowNegative: true` — a reconciled bank balance can be an overdraft). Known gap: the envelope allocate / move / top-up dialogs are shadcn `Input` inside dialogs that don't render `OrbitFormStyles`, so `OrbitCalcInput` can't drop in there unstyled — porting them is a separate change, not an oversight. All three current call sites must render **feedback line → `sr-only` live region → key strip** in that order; the drift card originally put the keys in between and bound its live region to the undebounced `message.text`.

- **Two states kept separate.** `draft` (local, in `useCalcField`) is exactly what the user typed; `value`/`onChange` is the _evaluated_ amount as a plain numeric string. Every existing `Number(amount)` call site is therefore untouched.
- **Incomplete, unreadable, or non-positive ⇒ emits `""`**, never a best-effort partial. `1200+340+` must not submit as 1540. `onBlur` runs `completeExpression` first and rewrites the visible field to the result, so the user watches `1200+340+` resolve to `1540`. Three traps there, each hit once: (a) it must repair the **raw** (alias-folded) text, never `normalizeAmountInput`'s output — feeding it a separator-stripped string hides the separators from `hasInvalidGrouping`, so `1200 340` came back as `1200340` on blur and the warning vanished, reinstating the fused-amount bug on the exact gesture that submits; (b) it must NOT auto-close unbalanced parens, which changes the expression's _shape_ (`2*(3+` → 6 for someone building `2*(3+4)` = 14); (c) it must return the input untouched when nothing was dangling, or every blur rewrites `1,250.00` to `1250` and marks an untouched edit-sheet row dirty. Blur only covers the pointer path — Enter submits without moving focus — so `useCalcField.onKeyDown` repairs and re-issues the submit on Enter, and all **five** calculator-enabled money guards word their toast for a field that may visibly hold something ("Enter a valid amount" / "Enter a valid fee" / "Enter a valid balance"), true whether it is empty or unreadable.
- **The feedback line is always mounted** with a reserved `min-height`. Conditional mounting shifted the key strip ~22px the instant an operator was tapped — under the user's finger. It shows `= 1,625.00` whenever the resolved total differs from what the field reads (which also catches the silent-rounding case: a typed `1.005` submits as `1.01`), and a warn-toned reason otherwise. `--warn`, not `--fg-4`: this is the only signal that Save is blocked, and `--fg-4` is the sub-contrast placeholder token.
- **A separate always-present `sr-only` live region** carries the announcement, debounced 700ms in the hook. A live region that enters the DOM together with its first content is commonly dropped by screen readers, and announcing per keystroke queues "= 1,203", "= 1,234", "= 1,540" while the user is still typing.
- **`emittedRef` guards the resync effect.** Without it, typing `12.50` round-trips through the parent as `12.5` and yanks the caret back a character. Only a `value` the hook didn't itself emit (a parent reset, an edit-sheet hydration) clobbers the draft.
- **`type="text"`, not `number`** — a number input rejects operator characters outright. `inputMode="decimal"` keeps the phone keypad numeric; the operator strip supplies what that keypad lacks. Removing `type="number"` also removed native `min="0"`/`step="0.01"`, so the hook's own non-positive rejection is what replaces them.
- **The key strip is `+ − × ÷ ⌫ =`, six keys in a fixed 6-column grid, all `tabIndex={-1}`.** Two grid traps here, both hit: the `=` key's mis-tap gutter must be `padding-right` on the _container_, because the keys are `width: 100%` of their grid area so a `margin-left` shifts one out of its track instead of narrowing it (the key hung 4px past the strip and into the drift card's column gap); and `.nt-drift-grid` had to move from a 480px to a 520px collapse breakpoint to match `.of-row`, because in the 481–519px gap the still-2-up drift card starved the strip to 24.03px tracks — on the WCAG floor in Chromium, under it in Firefox. `=` calls `field.resolve()`, which collapses the expression into its result _in the field_; it dims (`.is-idle`) rather than disappearing on a plain literal so the strip's geometry never shifts mid-entry. Grid, not wrapping flex — as flex the 44px touch keys overran the 238px card interior at 320px and broke to a second row with the backspace flung alone to the right; tracks now shrink to ~34.6px, still clear of the 24px floor. Hover/active fills are `color-mix`ed from the key's own `--bg-elev-3` base, never absolute elevation tokens: the strip sits on three surfaces (elev-2 amount card, elev-2 drift card, elev-1 drawer body for the fee), and a hard-coded `:hover` of elev-2 rendered at 1.00:1 — invisible — on two of them. Caret reads go through `caretRange`, which falls back to end-of-string unless the input is `document.activeElement`: `selectionStart` on a never-focused input is `0`, not `null`, so tapping `+` on an unfocused field holding `500` produced `+500` and the next digits landed inside it.
- **Resolving is a separate concern from validating, and the rule is "resolve whenever resolving changes the value".** `completeExpression` powers the `=` key, blur, and the first Enter. `1200+340` → `1540`; `1200+340+` trims the tail first and also → `1540`; but `1200.00` and `1,250.00` come back byte-identical, because the edit sheet seeds its amount from a pg `numeric` string and rewriting it on a stray blur marks an untouched row dirty. Shipping without this was a real gap: the readout said what _would_ be saved while the field kept reading `1200+340` forever, so the expression never became the number.
- **Enter resolves, then a second Enter submits.** Enter never fires `blur`, so it is the one path where the user would otherwise never see the resolved total before it saved — `1200×340+` (a plausible typo for `1200+340`) trims to 408,000 and posts it. `completeExpression` is idempotent, so once resolved the handler returns early and native submission takes over. `isComposing` is checked so an Android IME's keyCode-229 Enter doesn't trip it.
- **`hasInvalidGrouping` is load-bearing.** `normalizeAmountInput` strips `,`/space/`_` so a pasted `1,250.00` parses — which means `1200 340` (a missed `+`) would otherwise fuse into `1200340` and submit as ৳1,200,340, with no operator surviving to trigger the `= …` readout that would have contradicted the field. The guard requires valid grouping on every number literal, and accepts **both** comma conventions this app's users write: en-US `1,234,567` and South Asian lakh/crore `12,34,567`. (Rejecting the latter in a ৳ app tells someone their own locale's number is unreadable — a worse false negative than anything the guard catches, and both strip to identical digits so nothing downstream knows.) Space and `_` are stripped but never accepted as grouping: `100 200` groups validly by length and fused to 100200, and only its 4-digit lead caught `1200 340`.
- **The stack guard bounds nesting DEPTH, not input length, and must never be mirrored as `maxLength`.** `parseFactor` recurses per `(` and per leading unary sign, so a pasted `"(".repeat(5000)…` threw `RangeError` — and because `useCalcField` evaluates the draft _during render_, that escaped to the router's `errorElement` and replaced the page with the error boundary, destroying a half-filled form. Two wrong fixes preceded the right one, both worth remembering. A blunt 256-**character** cap rejected an ordinary 48-item receipt (287 chars); `parseExpr`/`parseTerm` are iterative, so a flat sum costs one frame no matter how long it is — only nesting matters, hence `MAX_NESTING_DEPTH = 64`. And mirroring the cap as `maxLength` on the inputs actively _reintroduced_ a silent-wrong-amount bug: the browser truncates an over-long paste without a word, and the truncated string still parses — that same 287-char receipt clipped to 256 chars cut `50.15` to `50` and resolved to 2,040.75 against a true 2,298.00, an 11% error every downstream signal agreed with. `MAX_AMOUNT_INPUT_LENGTH` (2000) survives only as a don't-reparse-a-megabyte backstop, and the inputs carry no `maxLength` so every rejection is visible.
- **`roundTo2` rounds through a _guarded_ `toPrecision(15)`, not an `EPSILON` nudge.** `Number.EPSILON` is the ulp of 1.0, so for `|n| >= 2` the nudge is a literal no-op — `8.165` rounded to `8.16`, and half of `4.27` came out a cent short. But `toPrecision(15)` is a _relative_ snap and can't be trusted at every magnitude either: by `|n| ~ 1e10` the scaled value has no fractional digits left, so the snap stops discarding a binary artifact and starts discarding a real cent (~3.4% of values in the 1e11–1e12 band, which `MAX_MAGNITUDE` admits). The snap is therefore taken only when it moves the value by less than a thousandth of a cent — provably byte-identical below 1e10 (700k-value diff), correct above. Rounding happens once at the end, never per operation; cent-exact addition chains were verified against exact rational arithmetic.

### EventSelect stale-row handling

`EventSelect` (`NewTransactionSheet.tsx:899`) injects a `"Closed" badge + name` row at the top of the dropdown when the form's `eventId` value points at a now-closed event (typically a hydrated pin whose event closed after the pin was set). The badge sits inside `.nt-stale-row` with `flex-shrink: 0` so the staleness signal survives the trigger's text-ellipsis on narrow viewports. Pair the surface here with the server-side `requireActive: true` guard in transaction create paths — the form gives the user a way to clear, and the server refuses to land a closed event even if they don't.

Pin feature:

- `pin.listBySpace` — read the `{ account, envelop, event }` trio on form open (used inside `usePins`). Real-space only.
- `pin.set` / `pin.clear` — mutations fired by `FieldPin`. Server gating: account = any member; envelope/event = owner|editor.

- `event.listBySpace` — event filter, real-space only (`TxEventChip`, hidden on `/s/me`).
- `transaction.listBySpace` + `personal.transactions` — paginated list via `useInfiniteQuery`, sends both the plural (`accountIds`/`envelopIds`/`expenseCategoryIds`) and (where still relevant) singular filter shape; each returned row carries `account_balances_after` for the Balance column.
- `transaction.filteredTotals` + `personal.transactionFilteredTotals` — IN / OUT / NET / AVG-DAY summary across the entire filtered set, not just the current page. Same filter input as the list query, memoized so the query key is stable across renders.

Mutations:

- `transaction.delete` -> calls `useInvalidateAnalytics(space.id)` from `@/lib/invalidate` (`:195-201`).
- New/Edit/Details sheets fire their own mutations and invalidations (see Files above).

## State & mutations

- Envelope/Account/Category filters live in the URL as `env`/`acc`/`cat` (repeated params, multi-value), owned by the shared `useAnalyticsFilters()` hook — the same URL shape the analytics Spending views use. Type/Event/Amount/User/search stay page-local URL keys: `type`, `event`, `user`, `q`, `min`, `max`, plus `period`/`from`/`to` (via `usePeriod`, default preset `"last-30-days"`, hoisted to the page-local `DEFAULT_PERIOD_PRESET` constant so `usePeriod()` and `<PeriodChip defaultPreset=...>` — two independent hook instances over the same URL params — can't drift apart). `resetFilters()` rebuilds the URLSearchParams from scratch keeping only `period`/`from`/`to`, so it clears every filter (env/acc/cat included) in one shot; it's wired as both the `AnalyticsFilterBar`'s "Clear all" and the page's empty-state "Clear filters" action.
- Search input is debounced 300ms (`useDebouncedValue`).
- Pagination is `trpc.transaction.listBySpace.useInfiniteQuery` / `personal.transactions.useInfiniteQuery` — tRPC manages the cursor itself (never pass `cursor` in the input object); changing any filter changes the query key and the list resets to page 1 automatically. `getNextPageParam` reads `nextCursor`; `null` on the latest page means end of data.
- `selectedTx` state opens the `TransactionDetailsSheet`; `editingTx` is a separate page-owned state so the details sheet can hand off to the edit sheet without the two Radix sheets ever coexisting.
- The "New transaction" CTA is wrapped in `PermissionGate roles={["owner","editor"]}` — same gate appears inline near each row's edit action.
- `activeFilterCount` (type/event/user/min/max only — deliberately excludes env/acc/cat, which the `AnalyticsFilterBar` owns and summarizes itself) badges the page's own filter affordances. `hasActiveFilters` is the broader OR of that count, `f.hasAnyFilter` (env/acc/cat), and search — it drives the page-level "no transactions match these filters" empty state and Clear button, so it must stay wider than `activeFilterCount` alone.

## Balance column

- Always rendered (not gated on any mode flag). Each row's `account_balances_after: Record<accountId, string>` comes straight off the list/personal query (see the server module docs) and is read via the local `rowBalanceEntries()` helper, which returns the source leg then the destination leg (From→To order) — one entry for income/expense/adjustment, two for a transfer.
- `isStatementMode` = exactly one account selected (`f.accountIds.length === 1`). It only changes rendering, not data: hides the per-row account color-dot (redundant when every row is the same account) and shows a `.tx-statement-note` banner. `AccountDetailPage`'s Transactions tab renders the same column for parity, reading `account_balances_after[account.id]`.
- The balance is the account's **true balance across its full history** (all spaces, ignoring the active filters and pagination) — it will NOT step by the visible row's amount once a non-account filter (type/event/user/amount/search) narrows which rows are shown, because intervening hidden rows still moved the account. The statement-mode banner and a lighter multi-account-mode caption (shown only when `activeFilterCount > 0 || search`) both call this out so it doesn't read as a bug.

## Conventions & gotchas

- Same filter object shape is reused for `listBySpace` and `filteredTotals`, but the totals query takes only filters (no `cursor`/`limit`); the input is memoized so react-query doesn't re-key per render.
- `period.start` / `period.end` come from `usePeriod` — the period is also URL-persisted.
- Personal-mode dispatch is everywhere: each query has a `Space` variant and a `Personal` variant, then `const x = isPersonal ? personal : space`. Don't forget to extend both sides (and the plural filter precedence) when adding a new filter — see the transaction/personal server module docs for the four places (`list`/`filteredTotals` × space/personal) that must stay in sync.
- Envelopes and (real-space) events are hidden in personal mode by forcing the URL-arg to `undefined`/`null` before it reaches the query (`envelopIdsArg`, `eventId`) — a stale `?env=`/`?event=` left over from switching from a regular space must not silently filter the personal list with no UI to clear it. Category filters are the exception: they work cross-space via `personal.listCategories`, so `categoryIdsArg` passes through unguarded.
- The page wraps inside `.orbit-design tx-root`; CSS is in the inline `TX_STYLES` template literal at the bottom.
- Money formatting uses `formatInAppTz` for dates and the local `UNALLOCATED_COLOR` for the unallocated chip color.
